추가로 찾아 고친 문제

- 정지 상태의 빈 입력이 서버 대기열에 남아 입력 처리를 계속 늦췄다. 정지 중에는 이동·새 점프가 없는 입력만 정리하고, 실제 입력보다 처리 번호가 계속 앞서가지 않게 했다. 물리 이동을 여러 번 실행해 따라잡는 방식은 사용하지 않는다.
- RTT 약 950ms에서 0.8초 투사체 표시 제한이 먼저 끝나, 나중에 받은 실제 투사체가 2~3유닛 뒤에 다시 나타났다. RTT와 미승인 입력 시간을 함께 이용해 응답 대기를 0.8~2.5초로 조절한다. 투사체별 수명도 같은 기준을 쓴다.
- 같은 조건에서 이동 승인 제한 0.75초가 정상 응답보다 먼저 끝나 약 3.9유닛 위치 보정이 발생했다. 이동도 같은 응답 대기를 사용한다. 수신 시각과 물리 업데이트의 시간 기준은 realtimeSinceStartupAsDouble로 통일했다. 시간 기준 통일만으로 입력 대기열 문제가 해결된 것은 아니다.
- 접속자 쿨타임이 서버 시간과 네트워크 시계 보정 때문에 늘어났다. 로컬 공격 대기는 로컬 경과 시간으로 계산하고, 서버의 공격 승인·재사용 제한은 유지했다. 서버가 거절하면 그 결과로 다시 맞춘다. 마녀의 로컬 연속 투척 간격도 같은 기준을 쓴다.

실제 Unity Services / Relay

Relay/Recheck02는 별도 인증 프로필 두 개로 실제 비공개 방 생성, 참가, 전투 진입, 이동, 공격 승인, 열린 공간의 투사체 연결, 상대 퇴장 결과, 양쪽 방 정리까지 8개를 통과했다. RTT 400ms에서 접속자 이동 표시 반응은 약 17ms였다. 접속자 카드 95프레임 궤적에서 연결 1회, 연결 간격 약 16.67ms, 역주행과 지형 접촉 외 비행 정지 0회를 확인했다. 종료 후 양쪽 모두 joined=false, busy=false다.

앞선 Relay/Recheck01에서는 참가 시간 초과가 있었으므로 연결 안정성이 모든 환경에서 해결됐다고 보지 않는다. 위 검사는 같은 Windows PC의 두 실행 프로세스와 실제 Relay 서비스를 사용했다. 서로 다른 PC·공유기에서의 장시간 인터넷 대전은 아직 확인하지 않았다. 피해 승인과 상대 상태 수신에는 실제 통신 시간이 남는다.

재현 자료

`Recheck.json`에 조건, 결과, 빌드·소스·원본 기록 해시를 저장했다. 원본은 `Logs/Move/<실행 이름>`과 `Logs/Relay/Recheck02`에 있다. 새 Run 이름으로 Flight.ps1 실행 후 Trajectory.py, Special.ps1 후 Specials.py를 실행한다. Cadence.ps1과 LagStep.ps1은 이번 회귀 검사를 추가한 스크립트다.

새 수정은 Assets/SSW 안에만 있고 코드 주석은 추가하지 않았다. 다른 팀원 소스·씬은 직접 수정하지 않았다. 최신 Base의 팀원 변경은 Git 병합으로만 반영했다. 기존 사용자 변경은 보존했다. 씬·배경·발판은 이번 수정 대상이 아니며 Unity CLI 연결 에디터는 MainMenu 편집 모드다.

시간 API 확인 자료: [Unity Time.unscaledTimeAsDouble](https://docs.unity3d.com/ja/6000.0/ScriptReference/Time-unscaledTimeAsDouble.html), [Netcode NetworkTime](https://docs-multiplayer.unity3d.com/netcode/1.13.0/advanced-topics/networktime-ticks/). 프로젝트에 설치된 NGO 구현도 함께 확인했다.
