# 방 수명 검증

## 재현

2026-09-27. Unity 6000.5.2f1, Multiplayer Services 2.2.4, NGO 2.13.2.

Base `383361f8c1d5e9565cb5a313cf70429cf3177cb8`, 프로토콜 20에서 에디터와 같은 소스의 개발 플레이어를 실제 UGS Lobby/Relay로 연결했다. 서로 다른 인증 프로필을 사용한 같은 PC 검사다.

`Logs/Room27/Before-20260927003522/Result.json`에서 혼자 있던 방의 정상 퇴장 후 조회 결과는 0개였다. 참가자가 있는 방에서 방장이 나가면 해당 방이 서버 조회에 1개 남았고, 참가자는 `joined=true`, `host=true`, `canStart=false`로 남았다. 이 프로젝트는 NGO 게임 상태의 호스트 이관을 구성하지 않는다. SDK의 로비 방장 선출과 실제 게임 호스트의 이관은 별개다.

이전 실행본과 에디터 사이의 NetworkConfig 불일치 검사는 재현 근거에서 제외했다.

## 변경

- 방장은 `DeleteAsync`, 참가자는 `LeaveAsync`로 종료한다. 서비스 정리가 성공하기 전에 로컬 방 참조를 버리지 않는다.
- 방 삭제, 방장 변경, 실제 네트워크 종료를 감지하면 남은 참가자의 세션을 정리한다. 일시적인 종료 실패는 재시도한다.
- 삭제 요청 실패와 삭제 성공 후 응답 유실을 구분한다. 이미 방에서 빠진 `NotInLobby` 상태도 처리한다.
- 목록을 열어 둔 동안 5초마다 조회한다. 실패하면 낡은 목록을 지우고 15초 후 다시 시도한다. 내용이 같으면 행을 다시 만들지 않는다.
- 목록 조회는 입장·생성을 막지 않는다. 새 작업이 시작된 뒤 도착한 이전 조회 결과는 적용하지 않는다.
- 없어진 방이나 네트워크 시작에 실패한 방은 목록에서 제거하고 30초 동안 재노출을 억제한다. 잘못된 비밀번호는 이 제외 조건에 넣지 않는다.
- 정상 앱 종료는 방 정리를 최대 5초 기다린다. 강제 프로세스 종료나 전원 차단에서 이 콜백이 실행된다고 가정하지 않는다.

`RoomCatalog`는 목록과 재노출 규칙을 담당한다. `MultiplayerSessionManager`는 세션 수명과 서비스 요청을 담당한다. 메뉴는 조회 시점과 표시를 담당한다. `NetGame`, `NetPlayer`, 전투·맵 및 프로젝트 설정은 이 기능의 편집 대상이 아니다.

## 검사 방법

프로젝트 루트에서 개발 플레이어를 `Builds/Rooms/Game.exe`로 빌드한다. 에디터와 플레이어의 소스 및 프로토콜을 맞춘다.

```powershell
unity command eval_file --file 'Assets/SSW/Tests/Rooms~/CatalogChecks.cs' --caller plugin --skill unity-cli --project-path . --format json
pwsh -File 'Assets/SSW/Tests/Rooms~/Verify.ps1' -Run FreshRooms
```

`Stage failures`는 오류 복구부터, `Stage shutdown`은 앱 종료부터 시작한다. `SkipAbrupt`는 강제 종료 검사를 생략한다. `Run`에는 새 이름을 사용한다.

검사는 실제 메뉴 버튼과 개발 빌드 전용 `MenuProbe`를 사용한다. `SessionFault`의 에디터 전용 대리 객체가 삭제 요청 전 실패와 삭제 성공 후 응답 유실을 한 번씩 주입하고, 즉시 원래 SDK 서비스로 복원한다. 읽기 검사에서 429 응답을 받으면 대기 후 재조회한다.

`room-editor27`, `room-runtime27` 테스트 프로필과 해당 실행이 생성한 방 ID만 정리한다. 공개 빠른 매칭으로 다른 사용자의 방에 참가하지 않는다. 에디터에는 플레이 루프 갱신을 요청하므로 프레임 지연 검증으로 사용할 수 없다.

## 최종 확인

2026-09-27, 프로토콜 21, 개발 빌드 `build_28643a4a8586`은 오류 0건, 경고 12건으로 완료했다. `Logs/Room27/After21B/Result.json`에서 같은 PC의 에디터와 개발 플레이어가 실제 UGS로 연결됐고 네트워크 설정 해시도 일치했다.

혼자 남은 방의 정상 삭제, 열린 목록의 자동 갱신, 참가자가 있는 방의 방장 퇴장과 참가자 정리, 일반 참가자 퇴장 시 방 유지, 같은 방 재참가를 확인했다. 테스트 종료 후 두 실행 모두 `joined=false`, `listening=false`였고 검사 실행 프로세스를 정리했다. 이전 테스트 프로필이 만든 지정된 방 ID도 소유자를 확인해 정리했다.

삭제 요청 전 실패와 응답 유실 뒤 재시도, 오래된 목록의 입장 실패 처리는 프로토콜 20의 `After08`에서 확인했다. 생성 취소와 목록 조회/생성의 동시 진행은 `After10`에서 통과했다. 이 실행의 이후 참가 실패는 플레이어 로그의 `NetworkConfig mismatch`로 분리했다. 최신 프로토콜 21에서는 설정 해시까지 비교해 정상 참가를 확인했다.

사용자의 마무리 지시에 따라 추가 회귀를 중단했다. 정상 앱 종료와 강제 종료 전체 시나리오는 최종 통과로 기록하지 않는다.

## 검증 범위의 제한

MPS 2.2.4에서 방 삭제와 참가자 퇴장이 겹치면 중지된 세션 핸들이 SDK의 `Sessions` 사전에 남을 수 있다. 기존의 세션 타입 교체 경로를 유지하며, 실제 서비스 소속이 없고 SDK 네트워크와 NGO 연결이 중지됐는지 확인한 뒤 재접속을 허용한다. SDK 내부 사전을 직접 수정하지 않는다. 사전 항목 개수만으로 실제 방이 남았다고 판정하지 않는다.

강제 종료 직후에는 서비스의 비활성 판정 전까지 방이 조회될 수 있다. 기본 비활성 필터를 덮어쓰지 않고 재조회와 입장 실패 복구를 사용한다. 서버에서 즉시 삭제된 것과 활성 조회에서 제외된 것을 별도로 기록한다.

실제 서로 다른 두 PC, 장시간 인터넷 단절, OS 강제 전원 차단은 이번 검증 범위가 아니다. 이전 공격 동기화 및 호스트 프레임 정지의 해결 증거로 사용하지 않는다.
